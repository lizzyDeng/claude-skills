# Router：一个 session 管全部待办，worker 并行修

> 状态：定稿待批准（2026-11-02，经四轮讨论 + 一次 builder check 整合）。
> 参考：DeepSeek Harness 团队《Super-agent》（2026-10-31，用户朋友转发；本地副本 aifriends 会话 4aae64da scratchpad `attention/wx/article.txt`）。
> 标注：**【用户定】** = 用户原话或明确裁决；**【我的决定】** = 设计者取舍，用户可推翻；其余留给实现者。
> 配套：HTML 版 `2026-11-02-router-design.html`；看板样例 `2026-11-02-router-board-mock.html`。

---

## 1. 为什么做

- 【用户定】「真人的注意力有限，管理 3–5 个 session 基本上是极限。」用户管 3 个 session 没问题，真正卡住的是串行：要等这 3 个修完，才派下一批。
- 【用户定】「周报出来之后，问题是清晰的。我需要在一个 session 里面管理接下来要做的事情，以及接受必须的决策任务，而不是我自己去等这些 session 完成。」
- 现状：router 这个角色现在由用户自己在当。读周报、拆问题、开 session、在 session 之间搬信息、逐个回答各 session 的提问，都是用户在做。
- 实例（11-02）：
  - 周报对照完以后，#940 里有 2 类问题当天就能并行开工，却都在等用户手动开 session。
  - 三个在跑的 run 同时在改 her 回复 prompt，它们之间的接口变化只能靠用户手工传话。

## 2. 目标 / 非目标 / 反目标

**目标**
1. 周报一出来，router 就备好派发单，每张票写明证据、优先级、依赖和要改的代码面。用户说 start 后派发；后续的票一解锁就自动接着派。
2. 必须由用户做的决定，只在一个地方做（router session）；全部状态在一个 UI 里看。
3. worker 之间的接口变化和新发现，由 router 按订阅转交，不再靠用户传话。
4. 方向在启动时就论证清楚，执行中很少停。

**非目标（v0 不做）**
- 24 小时在线、云端、跨设备（文章第 5 节）。router 只在这个 session 开着时工作；关掉再开，就从状态文件恢复。
- 文章 3.4 的投机执行（「静默复现并修复」）和 4.2 的多信道。
- router 自己写代码、自己定解法。
- UI 上的操作按钮。UI 只用来看。

**反目标（技术上能跑，也算失败）**
1. router 按症状派活。「她数落他」修了三次（#780 / #937 / #939），就是这么来的。router 只派**问题和证据**，解法由 worker 提出、用户确认。
2. 两张票同时改同一块代码，合并时互相打破字节冻结断言。
3. router 替用户做的决定，事后查不到依据。
4. 真实用户原话或 uid 进了 GitHub。
5. 用户被叫的次数比现在还多，或者 worker 频繁停下来回头找人。

## 3. 谁定什么

【用户定】「方案确认和花钱放行我来，其他交给 router」。另有两条用户已同意：上 prod 归用户定；「花钱」不包括 worker 自身的 Claude 用量。

| 决定 | 谁定 | 说明 |
|---|---|---|
| start（派本周派发单 / 某几张票 / 临时加的需求） | **用户** | 【用户定】周报出来后不自动开始 |
| 方案确认（确认的就是方向卡，见 §6.2） | **用户** | 进决定单 |
| 花钱放行：真 LLM 批量调用、生图、其他外部付费调用 | **用户** | 先报调用数和金额，跑完再报实际数 |
| 上 prod：合 main 发版、写 prod 库 | **用户** | 不可逆；写 prod 库本来就要真人登录 |
| 真人动手：staging 走查、登录、扫码 | **用户** | 不算决定，决定单里单列一栏「待你动手」 |
| 方向取舍、codex 分歧、优先级、拆票、依赖、何时派、合 staging（CI 绿后）、产品口径 | **router** | 每条写进 `decisions.md`，附理由和依据；用户可以说「推翻 Dn」 |

## 4. 架构（照搬文章第 2 节的双层，另加一张占用表）

### 4.1 Router（就是这个 session）
- 承接所有事件和用户消息。只做五件事：分诊、派发、转交、在授权范围内做决定、维护决定单和 UI。
- 不改仓库代码。
- 判断类的活交给 Opus 叶子：分诊、方向审、和 worker 讨论方向。【我的决定】文章说 router 用轻量模型就够；但在我们这里，拆错一次就会白跑一整张票。

### 4.2 Worker（每张票一个）
- 每张票一个 worktree，在里面后台跑 `claude -p … --output-format json`。【我的决定】
  - 进程一退出就是一个事件；`--resume <session_id>` 可以续跑；用户随时能用 `claude --resume <id>` 接管。
- worker 协议写在 router skill 内（`skills/router/worker.md`），**不改 conductor**。【我的决定】
  - 理由：新流程（§6）和 conductor 的 plan/grill/codex 两轮流程已经差得很远。单独写，就不用动用户的 conductor 护栏，也省掉回归验证。
  - conductor 的好规矩照搬过来：锚定 SHA、鲁棒性清单、验收时贴真实输出。
- worker 不直接问用户，只通过事件（§8）往上抛。

### 4.3 事件源
| 事件 | 来源 |
|---|---|
| 周报产出 | `~/.her-persona-daily/runs/<周一>/sent` 出现 |
| worker 停下 / 退出 | 进程退出 |
| worker 往上抛 | `.claude/router/events/<票>.jsonl` 追加 |
| PR 合并、CI 结果 | `gh` 轮询 |
| 用户消息 | router session |
| 定时巡检 | `/loop` 或 `ScheduleWakeup` |

### 4.4 占用表（文章里没有，我们加的）
- 每张票声明它要改的「代码面」。例：
  - her 回复 prompt（`prompt_builder.rs`、`prompt_template_en.rs`、`agent_loop/prompt.rs`、`her_chat/**`）
  - 角色数据
  - `llm_config`
  - 周报脚本
- 同一个代码面，同一时间只给一张票。后来的票排队，并在 GitHub 上挂 `blocked_by`。
- 派发时先预估要改哪里；方向卡出来后按实际更新。执行中如果要动别人锁着的代码，就是「要越界」，worker 停下（§8）。
- 代码面的定义放在项目配置里（aifriends：`.claude/router/surfaces.json`）。

### 4.5 巡检（简化版 watchdog）
- 进程还活着，但 ledger 超过 45 分钟没更新 ⇒ 读最后一段，判断是不是卡住了。判活看 ledger 的 mtime，不看 lsof。
- 同一步连续失败两次 ⇒ 进决定单。
- 起重票前先查共享 `CARGO_TARGET_DIR` 的大小（11-02 已到 141G）；票结束就清理。

### 4.6 状态（文章 5.1：计算和状态分离）
- `.claude/router/state.json`：每张票的状态、worker 的 session_id/pid/worktree、锁着的代码面、订阅、在等什么、各事件的时间。
- `.claude/router/decisions.md`：router 每做一个决定记一行，包括编号、时间、票、决定、理由、依据。
- router 被压缩或重启后，先读这两个文件。

## 5. 用户怎么用

### 5.1 一周的典型流程
1. 周一 09:00 周报出来。router 只分诊，备好派发单草稿，不建票、不起 worker，然后在 Lark 推一条提醒。【我的决定】
2. 用户打开 router：在主仓运行 `claude`，输入 `/router`。router 读状态、扫 worktree，认出用户自己开着的 session，登记它们锁着的代码。
3. 用户看派发单（session 里和 UI 上都有），说「start」「start 角色 周报」，或者「start，额度先不要」。到这一步，router 才建 issue、开 worktree、起 worker。
4. 派出去的每张票，方向卡在 30 分钟内交到用户手上（§6.1）。用户在 session 里回「A 同意」「C 改：…」，可以一次答好几条。
5. 用户去干别的。worker 执行中很少停；有决定要做时，Lark 推一条，只写件数和票号。
6. 上游合进 staging 后，同一批里排队的票自动解锁、自动派发，不用再说一次 start。【我的决定】用户临时提的需求，要单独说 start。

### 5.2 派发范围
【我的决定】派发单只收两类票：router 从周报分诊出来的，和用户在 router 里提的需求。已有的 backlog 要用户点名才收。

### 5.3 中途干预（在 router session 里直接说）
| 用户说 | 效果 |
|---|---|
| 「先停 A」/「立刻停 A」 | 先停：A 做完当前这一步就停。立刻停：直接停进程，worktree 和进度保留 |
| 「B 插队」/「C 往后放」 | 调整排队顺序 |
| 「告诉 A：…」 | 写进 A 的收件箱，A 在下一个检查点读到 |
| 「推翻 Dn」 | router 撤回这条决定，受影响的票带着新结论重跑 |
| 「我接管 A」/「还给 router」 | router 给出 `claude --resume <id>`，在用户说「还给 router」之前不再调度 A |

### 5.4 状态 UI
【用户定】要能看到：一共有哪些 issue、每个 issue 是什么状态，以及最重要的——**为什么派这个 issue，它解决什么问题，解法是什么**。

- 本地 HTML `.claude/router/board.html`。router 每次状态有变就重写，页面每 30 秒自动刷新。
- 页面从上到下：
  1. 计数和名额
  2. 决定单：按「挡住了几张票」排序，附上用户该回的话
  3. 全部 issue：可按状态筛选。每张卡分三栏：为什么派（周报证据、人数）、解决什么问题（根因 + `file:line`）、解法。卡片底部是占用、在等什么、接管命令、事件时间线、订阅清单
  4. router 最近做的决定，附推翻口令
- 【我的决定】「解法」一栏：方向卡出来之前，写 router 手上的线索，标「非方案」；方向卡出来后，换成方向卡摘要，并标明版本。router 自己不定解法。
- 样例见 `2026-11-02-router-board-mock.html`。

## 6. 一张票的生命周期

- 主线：待 start → 启动论证 → 等你确认方向卡 → 执行 → 验收 → 已合 staging → 等上 prod → 完成。
- 旁支：排队（写明在等什么）、需复核、暂停、你接管 / 卡住。

### 6.1 启动论证（【用户定】从派发到方向卡交到用户手上 ≤ 30 分钟）
【用户定】「在方案设计的时候，可以和 worker 多轻量化的讨论……不要花太多的时间做完整设计，需要在启动的时候就做好基本的论证和方案明确。」

| 时段（参考） | 谁 | 做什么 |
|---|---|---|
| 0–15 分 | worker | 读 issue 和证据，写方向卡；用最便宜的办法当场验证最关键的那条假设 |
| 15–25 分 | router ↔ worker | router（Opus 叶子）挑战 1–2 轮：这张卡解决的是不是派单时的那个问题？是不是在修症状？有没有更简单的做法？worker 据此改卡 |
| 并行 | codex | 只看一轮方向卡（`timeout 330`）；有分歧由 router 裁决，并标在卡上 |
| ≤ 30 分 | router | 方向卡进决定单 |

- 超过 30 分钟：router 照样把卡交出去，标明哪部分没完成、为什么。
- 如果验证最关键的假设要花钱：先转成花钱放行，方向卡上标「待验证」。

### 6.2 方向卡（一页）
1. 问题：派单时对应的周报指标和人数。
2. 根因假设：附 `file:line`，锚定到 SHA。
3. 方案方向：只写方向，不写完整设计。
4. 为什么不选另一种做法。
5. 核心假设：最多 3 条，每条写怎么验证；最关键的那条附上当场验证的结果。【我的决定】只论证不验证，正是「她数落他」修了三次的失败模式。
6. 验收标准：至少一条非 happy path。
7. 要改的代码面、预估工作量，以及这次改动会怎样推动派单时的那个指标。
8. 什么情况下会停（§6.3）。

### 6.3 执行：只在三种情况下停
1. 要花钱。
2. 方向卡上的核心假设被推翻（小偏差不算）。
3. 要动别的票锁着的代码。

除此之外，worker 自己决定，记成「发现」事件，不停。细节设计边做边定，不再出 plan v2、v3。

### 6.4 验收 → 合 staging → 上 prod
- 按方向卡上的验收标准执行，贴出真实的命令输出。
- CI 绿了以后，router 合进 staging，释放这张票锁着的代码面，并在下游票上留言：合了什么、SHA 是多少、对它有什么影响。
- staging 上的人工走查，进「待你动手」。
- router 把走查过的几张票攒成一批，上 prod 前等用户点头。发完后在周报的 `releases.json` 加一行，写明对应哪些指标。

## 7. 方向校验四层
1. **派发时**：派单写明为什么派（指标和人数）。
2. **启动时**：方向卡 + 当场验证 + router 讨论 + codex 一轮 + 用户确认（§6.1）。
3. **执行中**：核心假设被推翻就停（§6.3）；订阅的上游改了接口，就标「需复核」（§8）。
4. **合并后**：如果对应指标 2–3 周不动（先按样本量判断能不能下结论），router 重开这张票，标「方向可能错」。

## 8. 往上抛与订阅

**事件**：worker 往 `.claude/router/events/<票>.jsonl` 追加一行，router 实时收到。

| 类型 | worker 停不停 |
|---|---|
| 要决定（花钱，或方向卡确认之后又冒出来的方向问题） | 停 |
| 核心假设被推翻 | 停 |
| 要越界（要动别人锁着的代码） | 停，等 router 分配锁 |
| 改了接口（别人依赖的 prompt 段、函数签名、开关名、表结构） | 不停，通知订阅方 |
| 发现（对别人有用的事实；超出本票范围的新问题） | 不停 |

- 每条事件写清：哪张票、什么类型、三行以内的摘要、证据（`file:line` / SHA / 查询）、影响面（代码面、标签、相关的票）。
- 进度推进（方向卡出了、实现完了、合了）自动显示到 UI 上，不算事件。

**订阅**（文章 3.2 的 Thread，在这里换成「代码面 + 标签」）
- 每张票自动订阅三样东西：它依赖的票、它读或改的代码面、方向卡里声明的标签（例：「her 回复 prompt 底座」「llm_config chat 链」）。
- 快路径：影响面和订阅对得上，代码直接投递，不经过 LLM。慢路径：对不上时，由 router 判断谁该知道。
- 投递方式：
  - v0 用收件箱文件 `.claude/router/inbox/<票>.jsonl`，worker 每到一个检查点读一次。
  - 停着的 worker：收件箱内容随 `--resume` 一起带进去。
  - 用户自己开的 session：收件箱 + `SendMessage`。
- 收到「改了接口」或「假设被推翻」的订阅方，状态标为「需复核」，在下一个检查点核对自己的方向卡；如果自己的核心假设也被推翻了，就照 §6.3 停下。

## 9. 名额
- 【我的决定】分两类：
  - 重票（要编译 Rust）：最多 3 个同时在跑，用户自己开的 session 也算在内。
  - 轻票（数据、脚本、文案）：另算，最多 2 个。
- 在等用户回答的 worker，进程已经退出，不占名额，但它锁着的代码面继续锁着。

## 10. 约束
- 用户原话和 uid 不进 GitHub。worker 需要的话，router 给本地路径（`~/.her-persona-daily/…`，在仓外）。
- prod 只读（`supercli db query`）。worker 只写 staging；写了 staging 数据的票，要在同一个 run 里回滚。
- `~/.her-persona-daily` 不是 git 仓：改之前先整份备份，跑完由 router 核对。
- 角色设定这类数据，写成迁移文件，照常走 PR。
- 用户自己开的 session（11-02 时是 `aifriends-a6`、`aifriends-c2`），router 靠扫 worktree 和 ledger 认出来，只登记、只转交信息，不给它们下指令。
- headless worker 的权限要够它干活，但不能越过 prod 只读这条红线。

## 11. 成功标准
1. 周报出来后的下一次巡检时，派发单已经备好，每个问题都对应到一张票。
2. 用户说 start 后：每张方向卡在 30 分钟内交到用户手上；只要还有能做的票，名额就不空着。
3. 叫用户只有五种理由：start、确认方向卡、花钱、上 prod、真人动手。
4. 执行中 worker 停下的次数（不算方向卡确认）：每张票的中位数 ≤ 1 次。
5. router 做的每个决定，都能在 `decisions.md` 里查到理由。

## 12. 我替你定的（汇总，可推翻）
1. 周报到了就自动备派发单草稿（只做分诊）。一次 start 管整批，批内排队的票一解锁就自动派。
2. 派发范围：周报里分出来的票，加上你在 router 里提的需求；老 backlog 要你点名。
3. 完成点是合进 staging，这时释放锁；合 staging 由 router 来做。
4. worker 协议写在 router skill 里，不改 conductor。
5. 名额分重 3 / 轻 2；方向卡上最关键的那条假设必须当场验证。

## 13. 留给实现者 / 先做 spike
- skill 放在 claude-skills 的 `skills/router/`（`SKILL.md` + `worker.md` + 辅助脚本）；aifriends 专属配置放 `.claude/router/`。
- spike 先验证三件事：
  1. headless `claude -p` 能不能在 30 分钟内跑完启动论证，以及 Agent 工具在 `-p` 下能不能用。
  2. `--resume` 能不能接上停下时的状态。
  3. router session 关掉后，worker 进程能不能继续跑（`nohup` + pid 文件）。
- v1 再考虑用 `--input-format stream-json` 把消息实时推给正在跑的 worker。CLI 已经支持，但消息是插进当前这一轮，还是排到这一轮结束之后，还没验证。
- 巡检间隔、ledger 停滞阈值、名额数，按实测再调。
