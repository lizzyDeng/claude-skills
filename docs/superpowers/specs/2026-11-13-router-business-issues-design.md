# Router v2：票以业务问题为单位 + 分析 agent

> 状态：定稿（2026-11-13，经一次 builder check；§5.5 用户选「推荐」）。
> 前身：`2026-11-02-router-design.md`（v1，本稿只写改动；v1 里没被提到的部分照旧）。
> 标注：**【用户定】** = 用户原话或明确裁决；**【用户认可】** = 设计者提出、用户回「可以」；**【我的决定】** = 设计者的取舍，用户可推翻；其余留给实现者。
> 公开仓：本文不写任何项目的真实用户数据、原话或业务数值。项目专属的取数方法写在项目侧的 brief（项目自己的 gitignore 目录）。

---

## 1. 为什么改

- 【用户定】router 在第一个项目（her）上跑了两周。单张票都达成了目标，业务指标却没涨，第二周还变差了。用户原话：「诚然做了很多需求，单个需求都达成目标，但是我们整体的业务目标并没有得到任何提升。出差错的环节在哪里？为什么router 只会优先处理距离业务远的需求？」
- 复盘找到六处根因，都出在 v1 的设计上，不是哪个 worker 做错了：
  1. **入口**：分诊模板（`templates/triage.md`）规则 7 要求每张票的 `problem_anchor` 写到 `file:line`。只有能定位到代码的问题才成得了票；「角色不吸引人」「前几句不好玩」这类问题定位不到哪一行，所以永远进不来。
  2. **排序**：规则 10 写的是「先挡别人的、先合规风险、先当天能做完的」，决定单也按「挡住了几张票」排。排的是流程顺不顺，跟业务影响无关。
  3. **粒度**：规则 2「一个根因一张票」，于是一个用户问题被拆成一串机制票。例：「色欲用户被刹车、要图被拒就走」被拆成了调情开关、口味、要图给图三张票，每张单独验收，没有一张对用户问题本身负责。
  4. **验收**：上线验收先看机制，再按批统计行为。在小流量下，统计判定几乎全是「看不出来」，最后能报出来的只剩机制生效了没有。
  5. **发现**：问题只来自周报的固定分类，分类之外的看不见。两周里真正的新发现，都是用户追问出来的。
  6. **覆盖**：前端改动到不了新用户的第一段聊天。新前端要到下次冷启动才换上，而大多数新用户只打开一次。所以上线第二天去判前端改动，判的其实是没碰到改动的人。（单独修，见 §8）

## 2. 目标 / 非目标 / 反目标

**目标**
1. 【用户定】一张票 = 一个业务问题，具体做法是票里的任务。原话：「需要调整开票的优先级（业务指标增长为目的，而不是只是单点修复具体问题）。比如色欲满足是一个大的issue，具体怎么做是内部的task，而不应该把所有小问题拆分成独立issue」。另外，「不是让你只开这4-5个固定的issue」：票的数量随发现的问题变化，固定的是粒度，不是清单。
2. 优先级按业务影响排，不按挡住几张票排。
3. 【用户定】验收改成快速尝试、快速验证，不做 A/B。原话：「我不同意你做a/b，现在数据量这么点，而且本身迭代速度很快，你做A/B没有任何意义。你需要做的。快速尝试方向，快速验证。」
4. 【用户定】新增一个分析 agent，主动发现问题，真假由用户判。原话：「分析 agent 发现的新问题，我需要看一下是否是真问题，可以用fable 做这个agent」。
5. 【用户定】判效果之前先核覆盖。碰到改动的人是 0，就不判效果，先修覆盖（用户：「判法补充本身是对的」）。

**非目标**
- A/B、对照组、显著性检验，一律不做。
- 不改周报的 7 块版式（11-13 刚定）。分析 agent 的问题清单只加在第一屏。
- 不放松 v1 的红线：prod 只读，uid 和原话不进 GitHub，合 staging 要求 CI 全绿，花钱和上 prod 由用户定。
- 分析 agent 不写代码、不开票、不派活。

**反目标**（做到下面任何一条，就算失败，哪怕功能都能跑）
- 换个名字的小票：业务票里只塞一个机制就宣布做完；或者 router 继续按机制拆票。
- 分析 agent 只会复述周报分类，等于没加。
- 「验证」又退化成机制统计，或者退化成算显著性。
- router 或分析 agent 自己认定问题是真的，就直接开票。
- 不核覆盖就判效果。

## 3. 角色分工

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 用户 | 判问题真假；确认方向；放行花钱；放行上 prod；真人动手 | 拆任务、排任务、读数据 |
| 分析 agent（Fable） | 发现问题、估影响、写证据；每天验证前一天上线的改动；每周出诊断 | 写代码、开票、派活、动开关 |
| router | 把判真的问题开成业务票；按业务影响排序派发；把验证结论变成当天的调整；维护票和看板 | 自己判问题真假；自己定解法 |
| worker | 在一张业务票里试方向：实现、回放、上 staging，交给验证 | 越过票的范围开新票 |

## 4. 业务问题票

### 4.1 一张票写什么
- **人群**：哪群人（按项目的人群划分，或分析 agent 新发现的划分）。
- **想要什么**：他们来这里要的东西。
- **卡在哪**：在哪一步没拿到、离开了，也就是「墙」。墙可以有好几道，按先后列出来。
- **业务指标**：用哪个数衡量、现在是多少、往哪个方向变算好。
- **证据**：本地路径加聚合数字，不写 uid 和原话。
- **当前方向**、**任务清单**、**尝试记录**（每次尝试：做了什么、哪天上线、验证结论、下一步）。

### 4.2 票从哪来
业务票只有两个来源：
1. 分析 agent 提出、用户判为真问题；
2. 用户直接提。

router 不再从周报的异常直接出票。
- 【我的决定】用户回「真」就等于 start，router 开票后按优先级派发。暂时不想做，就回「真，先放着」。
- 维护项不用用户判真：分析 agent 在每周诊断里一并列出，由 router 排进维护票（见 §4.6）。

### 4.3 先归并，再开新票
新发现先看能不能挂到已开的业务票上，作为新的墙、新的任务或新的证据。挂不上，才作为新问题提给用户。判断标准是「是不是同一群人想要的同一件东西」，不看是不是同一个根因、同一个文件。
- 【我的决定】往已开的票上挂新墙，不用用户判真：问题本身已经判过真了。但每次挂墙都要写进当天的验证结论，用户能看到。

### 4.4 优先级
分析 agent 给每个问题估三样：人群规模、缺口（离「满足」差多少）、把握（证据有多硬）。用户判真的时候可以改。router 按这个排，不再看「挡住几张票」。

### 4.4a 一张票内部怎么跑
【我的决定】
- 一张业务票同时只有一个 worker，任务就是这个 worker 的清单项，不是 v1 意义上的票：不单独建 worktree，不单独出方向卡。
- 同一张票同一时间只能有一个尝试处在「已上线、待验证」，这样第二天读对话时，能知道是哪次尝试起的作用。
- 不同业务票可以并行。两张票碰到同一群人时，分析 agent 在验证结论里注明重叠。

### 4.5 什么时候结束
- 【我的决定】结束由分析 agent 提议、用户在每周清单里确认。提议的条件是两条同时满足：
  - 票上列出的墙都判了「有用」；
  - 这群人的业务指标连续两周往好的方向走。
- 【我的决定】连续 3 个方向都判「没用」：停下来，带着这几次尝试的结论回去找用户，问题本身可能要重新定义。用户可以改这个次数。

### 4.6 维护票
纯 bug、合规、基建、工具这类不对应任何用户问题的，每周合成一张维护票。
- 【我的决定】维护票同时最多占 1 个 worker 名额。
- 【我的决定】维护项的来源：分析 agent 每周扫一遍周报里的安全和合规指标、数据口径问题，以及 worker 上报的 bug，在诊断里列出来。v1 分诊的「方向可能错」复查票取消，由业务票的验证代替。`release_sync.unlabeled` 改由 router 巡检时直接转给用户。
- 例外：挡住验证或覆盖的（例如前端到不了新用户）直接开，不受名额限制，但要写明它挡住了哪张业务票。

### 4.7 现有票怎么迁
- 开着的、在上线验收中的旧票，按「同一群人想要的同一件东西」归到业务票下，成为它的尝试记录。
- 已经在实现中的票不打断，做完后计为对应业务票的一次尝试。
- 迁移清单由分析 agent 第一次跑时提出，用户判真时一起确认。

## 5. 尝试与验收：快速尝试、快速验证

### 5.1 一次尝试
一次尝试 = 一个方向。可以同时改好几处代码，但必须能用开关回滚。

### 5.2 上线前：离线回放
从真实对话的卡点（撞墙那一句）开始，用新版本重放，盲判墙还在不在。回放要花钱的，照常报价、等放行。

### 5.3 上线第二天：分析 agent 验证
按顺序做三步：
1. **覆盖**：数真实碰到新代码的人。前端改动看设备上报的前端版本，服务端改动看每轮快照里的新标记。碰到 0 人：不判，标「没入口」，router 当天查开关、部署和覆盖。
2. **读对话**：把碰到改动的人的对话全部读完，看两件事：那堵墙还在不在；他有没有接着聊下去（项目定的门槛，例如聊到 10 条）。
3. **判定**：
   - 有用：墙没了，他也接着聊了。保留，转去拆下一道墙。
   - 墙拆了、人没留住：墙没了，但他还是在门槛前走了。保留这次改动，从他离开前的几句里找出下一道墙，挂到票上（§4.3），下一次尝试拆它。
   - 没用：墙还在。当天换做法。
   - 有害：有人明显被伤到，或者护栏指标变坏。当天关开关撤回，并告诉用户。

【我的决定】分母和时机：
- 只算真正走到那道墙的人。碰到了新代码、但没走到墙的人（比如从没要过图），只计入覆盖，不计入判定。
- 走到墙的人不到 3 个：先记成「待样本」，每天重读，最长 7 天。7 天后有几个就按几个判。
- 几个人结果不一致：按多数判，同时把少数人的情况写出来。

样本小也照样判，写清楚看了几个人、几段对话。不算显著性。

### 5.4 每周
这群人的业务指标往哪个方向走，写进诊断。只看方向。

### 5.5 票级授权：票内换方向、上 prod 谁来批
【用户定】（11-13 选「推荐」）用户判一个问题为真时，就一次性授权了这一整张票。之后：
- 票内换方向，由 router 定：每次记一条 decide，写进当天的验证结论，用户看得到。
- 上 prod，由 router 做：每次上线都带开关；判「有害」当天关开关撤回，并告诉用户。分析 agent 判「没用」，router 当天换方向，不用先找人复核。
- 仍然要用户批的只有三类：
  1. 花钱（真 LLM 批量调用、生图等，照常报价）；
  2. 撤不回的改动（删数据、不可逆迁移）；
  3. 发应用商店包。
- 授权只覆盖这张票的范围（同一群人想要的同一件东西）。超出范围的事，按 §4.3 当作新问题提给用户。

## 6. 分析 agent

- **模型**：【用户定】Fable（`claude -p --model claude-fable-5-1`，走订阅，不算花钱）。
- **输入**：
  - 本机上的真实对话原文；
  - prod 的只读聚合数据和埋点；
  - 周报的 summary 和上线流水；
  - 业务票的状态；
  - 应用商店的评论（取得到的话）；
  - 业内资料（联网查）。
- **方法**（不套周报分类，项目 brief 写具体取数）：
  1. 每天读完前一天新用户的第一段对话；
  2. 对比「第二天回来的人」和「没回来的人」，第一段聊天有什么不同；
  3. 看每个人离开前的最后几句：她说了什么，他说了什么；
  4. 看漏斗每一环掉在哪；
  5. 看已开业务票的墙还在不在。
- **产出**：
  - 【用户认可】每天：前一天上线改动的验证结论（§5.3）交给 router，router 当天照结论调整。新用户首聊里只要有新发现，就作为候选问题记下。
  - 【用户认可】每周：一份诊断，加一份新问题清单。清单每一条写：人群、想要什么、卡在哪、证据、影响估计、建议指标。清单放在周报第一屏，同时进决定单，用户逐条回「真」或「不是：理由」。
- **记忆**：用户判「不是」的问题类型要记下来。以后不再提同类，除非有新证据，并且写明新在哪。
- **校准**：【用户认可】第一次跑时不给它已知结论，看它能不能从原始数据里自己找出 her 已知的三个问题：要图被拒就走、新用户首聊用的是旧前端、来的人结构变了。找不出来，就先修方法再用。
  - 【我的决定】校准单独跑一次：输入里不给业务票状态、不给已有票的标题，只给原始数据和时间范围。
  - 过没过由 router 对照这三个已知问题判，结果连同它找到的其他问题一起交给用户看。
  - 迁移清单（§4.7）在校准通过后另跑一次。
  - 校准通过之前，新问题只由用户直接提；在做的票照常做；v1 的分诊不再运行，不做双轨。
- **红线**：真实数据只在本机读；进 GitHub 的只有聚合数和改写过的描述；不写库，不动开关。

## 7. router 要改的地方（实现清单）

1. 分诊：`templates/triage.md` 换成分析 agent 的模板，每日、每周各一份。router 不再直接从周报出票。
2. 票：数据里加 `kind`（`business` / `maint`），加上业务票的字段（§4.1）、任务清单和尝试记录。
3. 排序：按 §4.4。决定单的排序也按业务影响。
4. 决定单：新增「问题判真」一类，用户回「真」或「不是：理由」。
5. worker：业务票的 worker 循环是「方向 → 实现 → 回放 → staging → 上线 → 等验证结论 → 下一个方向」。同一张票的多次尝试共用一个工作上下文；worktree 是常驻还是每次尝试新开，留给实现者定。
6. 上线验收：业务票改走 §5.3 的三步；维护票保留 v1 的验收。
7. 看板：按业务票展示，每张显示指标、当前的墙和尝试记录。
8. 周报第一屏：放问题清单。怎么接进项目的周报，由实现者和项目 brief 定。

## 8. 前提：前端覆盖

前端改动要能当天到达新用户的第一段聊天，否则 §5.3 对前端改动无效。这件事在项目侧单独修（her：T100，用户已 start），不在本次 router 改动范围内。

## 9. 约束

- claude-skills 是公开仓。不写真实 uid、原话和业务数值；push 前用防泄漏闸扫 `git log -p`，命中数必须为 0。
- 花钱、撤不回的改动、发应用商店包，仍然由用户批；票内换方向和上 prod 按 §5.5 的票级授权。
- `claude -p` 走订阅，不算花钱；真 LLM 回放照常报价。
- 现有 router 测试要继续全绿。新行为先红后绿。
