Router：一个 session 管全部待办

设计稿 · 定稿待你批准 · 2026-11-02 · 参考 DeepSeek《Super-agent》双层架构
一句话：周报出来后，router 先把派发单备好；你说 start 它才开始派。每张票 30 分钟内交一页方向卡给你确认，确认后 worker 一路做下去，只有三种情况会停。worker 之间的消息靠订阅自动转交。你只在一个 session 里说话，在一个看板上看状态。
批准前请看这 5 条是我替你定的，可以推翻
  1. 周报一到就自动备派发单草稿，只做分诊。你说一次 start 管整批：批里排队的票解锁后自动派，不用再说。
  2. 派发范围：只收周报里分出来的问题，加上你在 router 里提的需求；老 backlog 你点名才收。
  3. 一张票合进 staging 就算完，这时释放它的锁；合 staging 由 router 做（等 CI 绿）。
  4. worker 的流程写在 router 里，不改 conductor，你自己开的 conductor 照旧。
  5. 名额分重 3、轻 2。方向卡上最关键的那条假设，必须当场验证一次。

1为什么做

  • 你说的：3 个 session 你管得过来，卡你的是串行：要等它们修完才派下一批。可周报一出来，问题就已经清楚了。
  • 现在是你在当 router：读周报、拆问题、开 session、在 session 之间搬信息，一个个回答它们的提问。
  • 11-02 的实例：#940 里有 2 类问题当天就能开工，却在等你开 session；三个 run 同时在改 her 回复 prompt，它们之间的接口变化全靠你手动传话。

4你怎么用

一周的流程

  1. 周一 09:00 周报出来router 只分诊，备好派发单，不建票、不起 worker；Lark 推一条提醒。
  2. 打开 router在主仓运行 claude，再输入 /router。它会认出你自己开着的 session，并登记它们锁住的代码。
  3. 看派发单，说 start可以说「start」，也可以挑着说，比如 start 角色 周报、start，额度先不要。说完它才建 issue、开 worktree、起 worker。
  4. 30 分钟内收到方向卡一次能回好几张，比如 A 同意，C 改：……
  5. 去干别的worker 基本一路做到底。需要你时 Lark 推一条；上游的票合进 staging 后，同一批里排队的票会自动派出去。

中途干预：直接说

你说效果
先停 A / 立刻停 A「先停」等当前这一步做完再停；「立刻停」直接停进程，worktree 和进度都保留
B 插队 / C 往后放调整队列顺序
告诉 A：……写进 A 的收件箱，A 到下一个检查点会读到
推翻 D3撤回 router 的这条决定，受影响的票带着新结论重跑

看板

能看到全部 issue、各自的状态，以及为什么派、解决什么问题、解法是什么。「解法」一栏在方向卡出来之前，只写 router 掌握的线索，并标注「非方案」。router 每次状态有变就重写看板，页面每 30 秒自动刷新。样例：2026-11-02-router-board-mock.html。

5一张票怎么走

你start
≤ 30 分钟启动论证 → 方向卡
你确认方向卡
一路做完执行 → 验收 → 合 staging

启动论证（你定的：30 分钟以内）

时段谁做什么
0–15 分worker读 issue 和证据，写方向卡；用最便宜的办法（复现一次、查一条 SQL、跑一个现有测试）当场验证最关键的那条假设
15–25 分router ↔ worker挑战 1–2 轮：解决的是不是派单时那个问题？是不是在修症状？有没有更简单的做法？
并行codex只看一轮方向卡；有分歧由 router 裁决，并标在卡上
≤ 30 分router方向卡进你的决定单；超时就照常交，并写明哪些还没做完

方向卡：一页 8 项

问题 · 根因

派单对应的周报指标和人数；根因附 file:line，锚定到 SHA。

方向 · 为什么不选别的

只写方向，不写完整设计。

≤3 条核心假设

每条写明怎么验证；最关键的那条附上当场验证的结果。

验收 · 范围 · 何时停

至少一条非正常路径；要改哪些代码面、工作量多大、怎么推动指标；什么情况下会停。

执行：只在 3 种情况停

  1. 要花钱报价，等你放行。
  2. 方向卡上的核心假设被推翻小偏差不算，worker 自己定，记成「发现」。
  3. 要动别的票锁着的代码等 router 分配锁。

细节设计边做边定，不再出 plan v2、v3。拿内心泄漏那张票来比：grill 32 分钟、修订 26 分钟、codex 两轮都没过，最后还是交给你裁决，方案阶段前后花了好几个小时。

6方向对不对：四层校验

  1. 派发时派单写明为什么派：对应的指标和人数。
  2. 启动时方向卡 + 当场验证 + router 讨论 + codex 一轮 + 你确认。
  3. 执行中核心假设被推翻就停；订阅的上游改了接口，就标成「需复核」。
  4. 合并后对应指标 2–3 周都不动（先看样本量够不够下结论），router 重新开票，标注「方向可能错」。

7往上抛与订阅

事件worker例子
要决定停花钱；方向卡确认之后又冒出来的方向问题
核心假设被推翻停根因不对、复现不出来、数据和预想相反
要越界停要动别人锁着的代码
改了接口不停改了别人依赖的 prompt 段、函数签名、开关名、表结构 → 通知订阅方
发现不停对别人有用的事实；超出本票范围的新问题（router 决定要不要建票）
  • 订阅：每张票自动订阅三类东西：它依赖的票、它读或改的代码面、方向卡里声明的标签。能对上订阅的，由代码直接投递；对不上的，由 router 判断谁该知道。
  • 投递：v0 用收件箱文件，worker 每到一个检查点读一次；停着的 worker 在 --resume 时一起带进去。实时推送要等 spike 验证 --input-format stream-json 后再上。
  • 例子：内心泄漏那张票改了底座 prompt 的前缀表，会发一条「改了接口」。AI 口径和对话质感两张票都订阅了「her 回复 prompt 底座」，会立刻收到并标成「需复核」。这一步现在靠你手动传话。

9怎么算成功

  1. 周报出来后的下一轮巡检派发单已备好，每个问题都对应到一张票。
  2. start 之后每张方向卡在 30 分钟内交到你手上；只要还有可做的票，名额就不会空着。
  3. 叫你的理由只有 5 种start、方向卡、花钱、上 prod、真人动手。
  4. 执行中停下的次数每张票的中位数 ≤ 1 次（不算确认方向卡）。
  5. router 替你定的事在 decisions.md 里都能查到理由。

10不做 · 风险 · 先验证

不做：24 小时在线

Mac 合盖或 session 关掉，router 就停；重新打开后从状态文件恢复。

风险：根因判错

方案阶段变轻了。兜底有两道：开工前的当场验证，合并后看指标有没有动。

先验证：headless 能不能 30 分钟跑完

Agent 工具在 -p 模式下能不能用，--resume 能不能接上，router 关掉后 worker 还活不活。

风险：权限

headless worker 要能干活，又不能碰 prod 写操作。
