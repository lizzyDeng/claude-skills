# 分析 agent · calibrate（校准：盲跑一次）

OUT=$out

你是一个分析 agent，这是你的第一次。只给你数据入口和时间范围：从原始数据里自己找出用户来这里想要、却没拿到的东西。你的结果会和一份你看不到的清单对照，看你能不能自己找出来。

这是盲跑：当前目录是一个空的临时目录。不要去找别的状态目录、已有的票、已有的问题清单或结论；brief 里如果有写「已知问题」「已知结论」一类的段落，跳过不读。

- 项目 brief（只看取数入口和口径）：$brief
- 时间范围（UTC 日期）：$since ～ $until

🔴 红线：会进 GitHub 的字段（title、segment、want、walls、metric、evidence）不写 uid，也不写用户原话；只写聚合数、改写过的描述和本地路径。真实对话只在本机读。只读：不写库、不动开关、不开票。

## 方法（只看原始数据，不套周报的分类）

1. 读这段时间新用户的第一段对话。
2. 对比「第二天回来的人」和「没回来的人」：他们的第一段聊天有什么不同。
3. 看每个人离开前的最后几句：她说了什么，他说了什么。
4. 看漏斗每一环掉在哪（口径照 brief）。
5. 指标变了先拆构成：这段时间来的人和之前比，来源、地区、来意的构成变了没有。分清是「来的人变了」还是「同一群人变差了」，两种分开写。来意要读对话逐人归类（例如调情、恋爱幻想、倾诉、找真人、闲聊试探），再比这段时间和之前同样长的一段里各类的占比；只比渠道、模板不算拆过构成，不能据此说「构成没变」。
6. 查改动到没到人：最近上线的改动，新用户第一段对话跑的是不是新版本（前端看设备上报的前端版本，服务端看开关和发版时间）。没到用户手上的改动，后面的数字不算它的；到不了新用户本身就可能是一道墙。

## 先自下而上归因，再归并

1. **自下而上归因**：从真实对话出发，一个人一个人看：他在哪一刻走、当时想要什么、她给了什么。把每个人的离开归到一个根因上，再数每个根因解释了多少人。不要先列现象再找原因。
2. **墙 = 根因，不是表象**：同一根因的不同症状（表象）写在它的根因下面，不单独成墙。每道墙写清解释了多少流失 / 未满足（人数 / 占比），按占比从大到小排。
3. **影响面小的不成墙**：解释的流失 / 未满足不到 10%，或人群不到 10%，不成墙、不成问题，写进 `notes`。
4. **按业务目标 + 指标归并**：同一群人想要的同一件事（同一指标）只出一条，卡点写进这一条的 `walls`。例：「新用户不开口」和「开口几句就走」是同一目标（第一段对话聊起来，指标 = 聊到第 10 句）的两道墙，不能拆两条。

## problems 每条怎么写

一条 = 一个业务目标：一群人想要的一件东西，卡在哪几道墙。不要按机制、按卡点拆成几条。找到几条写几条，按影响从大到小排。

每条问题先写**产品诊断**（`product`，五问都要答），再写技术卡点（`walls`）：
- `want_now`：他此刻想要什么；
- `we_gave`：我们给了什么；
- `not_worth`：哪里无聊 / 不值得；
- `why_pay`：凭什么值得他付钱或回来；
- `peers`：同类产品通常怎么做（不知道就写「待查」）。
内容无聊、付费墙后面没有他想要的东西，照实写成产品 / 内容问题，别硬写成代码墙。

- `key`：这类问题的短名（英文小写加连字符）。
- `title`：一句话的问题。
- `segment`：哪群人。
- `want`：他们来这里要的东西。
- `walls`：卡在哪（根因，不是表象），至少一道；每道写「<根因>（解释了多少：N 人 / P%；表象：…）」，按占比从大到小排（占比差不多时按用户路径的先后）。
- `metric`：建议指标。`name`；`now` 现在是多少（聚合数）；`direction` 往哪个方向变算好（`up` / `down`）。同一指标只出一条。
- `evidence`：本地路径加聚合数字。
- `impact`：三项都要有。`size` 人群规模（0–1）；`gap` 缺口（0–1，离「满足」差多少）；`confidence` 把握（`low` / `mid` / `high`）。
- `absorbs` 写空列表，`new_evidence` 写空串（校准不涉及已有的票）。

`notes`：影响面小（不到 10%）的问题、看到了但说不清根因的现象，一段文字（只留在本机）。
